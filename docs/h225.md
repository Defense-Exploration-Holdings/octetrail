# H.225.0

`octetrail.h225` parses and packs H.225.0 call signaling messages the way
dpkt 1.9.8 does. `H225` and `H225.IE` use the [`Packet`](packet.md) base, as in
dpkt, and the information element boundaries are found in Rust. The module has
dpkt's message and information element constants.

```python
from octetrail import h225

raw = bytes.fromhex("0300000b0802000105" "28024869")
packet = h225.H225(raw)
assert packet.type == h225.SETUP
assert [(ie.type, ie.data) for ie in packet.data] == [(h225.DISPLAY, b"Hi")]
assert bytes(packet) == raw
```

## Fields

A message is read from inside its [TPKT](radius-rtp-stun-tpkt.md) header,
which is kept as `tpkt`. `H225` has `proto` and `ref_len`, then `ref_val`
(`ref_len` bytes), `type` and `data`, a list of `H225.IE`.

An information element has `type`, `len` and `data`. A type with the high bit
set has no length or value. Type 126 (`USER_TO_USER`) has a 2-byte length, and
every other type has a 1-byte length. A length that runs past the end of the
buffer keeps the bytes that are there, as in dpkt.

## Packing

`bytes()` packs the TPKT header, the header, `ref_val`, `type` and each
element, without updating the TPKT length. As in dpkt, `len()` counts the TPKT
header, the header and the elements, but not `ref_val` or `type`.

## Errors

- A TPKT version other than 3, a nonzero reserved byte and a TPKT length past
  the end of the buffer raise `UnpackError` with dpkt's messages.
- A buffer shorter than the TPKT header raises `NeedData`. A message cut off
  before its type, and an element cut off inside its length, raise
  `UnpackError` with dpkt's messages.

dpkt slices the rest of the buffer once per element, so a message with many
elements takes quadratic time. OctetRail finds the elements in one pass.

## Verification

The [fixture driver](../tools/h225_differential.py) parses 87 messages,
including prefixes of dpkt's SETUP vector. It also builds and edits messages
and elements. OctetRail must equal dpkt 1.9.8 on all 95 observations, with no
declared differences:
